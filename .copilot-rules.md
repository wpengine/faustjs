# GitHub Copilot Rules for FaustJS Repository

## Project Structure Guidelines

### Licensing

- **Main packages** (`packages/`): Use MIT license
- **Examples** (`examples/`): Use BSD Zero (0BSD) license
- **Archive/Legacy** (`archive/`): Maintain existing licenses (typically MIT)
- Always update `package.json` files with correct license field when creating new packages

### Package Management

- Use `pnpm` as the package manager (specified in `packageManager` field)
- Maintain consistent versioning across related packages
- Use scoped packages with `@faustjs/` or `@faustwp/` prefixes appropriately

### Directory Structure

- `packages/` - Core library packages (astro, core, nextjs, react)
- `examples/` - Example applications and tutorials
- `archive/` - Legacy packages (faustwp-cli, faustwp-core)
- `docs/` - Documentation (explanation, how-to, reference, tutorial)
- `plugins/` - WordPress plugins
- `site/` - Project website

## Development Philosophy

### Simplicity Over Complexity

- Start with the simplest solution that works, then add complexity only when absolutely necessary
- If you find yourself building complex abstractions, step back and ask if a simpler approach exists
- Prefer explicit, obvious code over "magic" that hides implementation details
- Question whether template registries, complex HOCs, or automated systems are actually needed

### Headless-First Design

- Don't take over entire systems (routing, rendering, etc.) - provide utilities that developers can compose
- Give developers control over their implementation rather than imposing opinionated frameworks
- If it feels like "magic," it's probably too opinionated for a headless system
- Provide core utilities and let developers implement their own data fetching and routing logic

### Reuse Before Reimplementing

- Check if functionality already exists in shared packages before writing new code
- When improving shared functionality, update the shared package rather than working around it
- Don't duplicate logic across framework-specific implementations
- Use existing functions like `getTemplate` instead of reimplementing the same logic

## Technical Implementation Guidelines

### Environment Variables

- Use semantic names (`WORDPRESS_URL`) over technical ones (`GRAPHQL_ENDPOINT`)
- Let packages handle technical details (like appending `/index.php?graphql`)
- Default to WordPress conventions (prefer `/index.php?graphql` over `/graphql`)

### Framework Organization

- Keep framework-agnostic utilities at main package level
- Put framework-specific code under subpaths (`/pages`, `/app`, etc.)
- Each framework handles its own specific needs (paths, imports, etc.) in its own layer
- Example: Astro needs file paths, Next.js only needs template IDs

### Dynamic Imports Structure

- Use `next/dynamic` in template index files, not in page components
- Keep loading states and code splitting organized at the template level
- Import the configured templates directly in pages
- Structure: `wp-templates/index.js` exports dynamic components, pages import and use them

### Backward Compatibility

- Don't add complexity for unreleased versions
- Clean up deprecated patterns before they become public API
- Focus on the best API design rather than supporting every iteration
- Remove fallbacks for functionality that was never released

## Code Standards

### TypeScript/JavaScript

- Prefer TypeScript for new packages
- Use consistent tsconfig.json configurations
- Follow existing code style and formatting patterns
- Include proper type definitions

### Package.json Requirements

- Include `license` field with appropriate license
- Use `packageManager` field to specify pnpm version
- Include proper `engines` field for Node.js version requirements
- Use consistent naming conventions for scripts

### Documentation

- Always include README.md files for new packages
- Update documentation when making significant changes
- Follow existing documentation structure in `docs/` folder

## Development Workflow

### File Operations

- Always use absolute paths when working with files
- Check existing file contents before making edits
- Include sufficient context (3-5 lines) when using replace_string_in_file
- Prefer reading larger file sections over multiple small reads

### Testing and Validation

- Check for errors after making file changes
- Validate package.json syntax and structure
- Ensure new packages follow existing patterns

### Git and Repository

- Respect the current branch (canary) and repository structure
- Be mindful of changes that affect multiple packages
- Consider impact on both development and production environments

## Specific Project Guidelines

### FaustJS Context

- This is a headless WordPress framework for React/Next.js
- Maintain compatibility with WordPress and GraphQL
- Consider both developer experience and end-user needs
- Follow WordPress and React best practices

### Legacy Support

- Archive folder contains legacy packages that may need different treatment
- Be careful when modifying archived packages
- Consider migration paths when updating core functionality

## Error Handling and Debugging

### Common Issues

- Always verify file paths are correct and absolute
- Check for syntax errors in JSON files after editing
- Validate that new packages can be properly installed and used
- Consider dependencies and peer dependencies

### Tool Usage

- Use appropriate tools for each task (don't use terminal commands when file tools are available)
- Prefer semantic search for understanding codebase structure
- Use grep search for specific string patterns
- Read files in meaningful chunks rather than line by line

## Quality Assurance

### Before Completion

- Verify all package.json files have correct license fields
- Ensure new files follow existing patterns and conventions
- Check that all created files are properly formatted
- Validate that changes don't break existing functionality

### Best Practices

- Maintain consistency with existing code style
- Follow semantic versioning for package versions
- Keep dependencies up to date and secure
- Document any breaking changes or migration requirements
